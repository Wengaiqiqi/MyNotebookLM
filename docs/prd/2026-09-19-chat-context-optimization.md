# MyNotebookLM：现有聊天链路优化 PRD 与执行文档

日期：2026-09-19

版本：v2.0（执行设计；功能尚未实施）

范围：现有项目级 RAG 聊天链路；本轮只交付文档，不实施代码修改。

阅读顺序：第 1～10 节是产品要求；第 12～20 节是落实这些要求的技术约定；第 21 节是按依赖排序的执行清单，第 22 节是交付检查。技术名称是拟新增或拟调整的接口，不代表当前代码已经实现。后文给出的内部参数作为实现起点，完成对照测试后才能称为已验证配置。

## 1. 产品目标与已确定边界

在现有“项目资料检索 → 组装历史及证据 → 流式回答”链路上，提高资料覆盖、多轮连续性和长回答可靠性，同时控制检索、数据库读取和生成开销。

已确定：

- 当前项目导入的资料全部属于使用范围，没有“当前选中的资料”概念，也不新增资料选择器。
- 实际参与聊天检索的是当前项目中状态正常、当前版本已就绪并可检索的资料；导入中、处理失败和删除中的资料不被视为已经读取。
- 不新增“自动 / 全面”切换，不新增全面阅读、分批阅读、汇总流程，不为未来模式预留空接口。
- 编辑提供商配置的界面、字段和操作保持原样。
- 当前的“编辑模型配置”入口调整为“编辑提供商配置”，继续保留现有提供商级字段、批量模型发现、URL、凭据和相关操作。
- 在具体模型行上新增独立的“编辑模型配置”入口；该窗口只显示和配置上下文容量、最大输出长度，不显示或编辑 URL、Key、模型 ID、模型列表、提供商路由和其他提供商级字段。
- 延用现有检索、流式输出、引用、取消、重试和备用模型路由。
- 本期参数的预算行为作用于聊天发送、重新生成、现有聊天重试及手动继续生成路径。工作台转换、标题生成、嵌入及其独立预算不在本期改造范围；模型配置中需说明这一作用范围。

## 2. 已确认的产品决策

用户已确认以下三项。未知容量的具体默认值、历史预留比例、候选扩展参数等仍是文档中的建议起点，不代表已完成性能验证。

| 编号 | 问题 | 决策状态 | 内容 |
| --- | --- | --- | --- |
| Q1 | 无法获取模型容量且用户未填写时怎么办？ | 已确认 | 使用明确标注的保守默认值，允许直接使用；具体默认容量仍为方案建议 |
| Q2 | 默认最大输出长度是多少？ | 已确认 | 8,192 tokens（8K），允许模型级调整 |
| Q3 | 达到输出上限时本期做什么？ | 已确认（按最新补充） | 保留回答及上限提示，增加手动“继续生成”；保留重新生成及编辑模型配置入口，不自动续写 |

“重新生成”从原问题重新回答；“继续生成”是新的模型请求，基于已有回答接写。两者均受每次输出上限约束，都可能再次截断。继续生成不会自动提高额度，也不承诺一次补完全部回答。

## 4. 模型高级配置

### 4.1 界面与保存范围

#### 编辑提供商配置

当前提供商级编辑入口改名为“编辑提供商配置”。它的字段、行为和保存范围保持现有实现，不因本期上下文优化而删减或迁移字段。它继续负责提供商地址、凭据、模型发现、模型列表及提供商级模型配置操作。

#### 编辑模型配置

具体模型行上的编辑入口命名为“编辑模型配置”，与“编辑提供商配置”分开。点击后只编辑当前模型的高级参数。可通过弹窗标题标识目标模型，但不增加模型 ID 或提供商信息表单行；表单只提供以下两个配置项及各自的“恢复默认”操作：

| 字段 | 说明 | 默认及来源显示 |
| --- | --- | --- |
| 上下文容量（tokens） | 用于本期聊天输入与输出预算核算 | 显示服务商数据、已确认资料、手动设置或未确认默认值 |
| 最大输出长度（tokens） | 一次聊天生成的上限，不要求回答写满 | 默认 8,192；可以手动覆盖，受已知模型能力约束 |

要求：

- 保存只修改目标模型配置 ID 的高级参数，不改变 URL、凭据、模型 ID、模型路由、启用状态及同组其他模型。
- 两个入口必须使用不同的编辑上下文和保存请求；打开“编辑模型配置”不能出现提供商编辑表单，也不能触发模型发现或批量模型保存。
- “编辑提供商配置”继续保留现有行为；修改提供商配置后，不得清除或覆盖模型的上下文容量、最大输出长度高级参数。
- 同名模型在不同提供商配置下可拥有不同参数。
- 提供商批量保存时，未提交的高级字段必须保留；明确恢复默认才清除手动覆盖。
- 不将保存高级参数与联网发现或连接测试捆绑。离线、服务商暂不可用时仍可保存合法配置。
- 前后端都校验正整数、可表示范围及已知能力约束；不能接受空值被意外转成零、负数、小数、无穷大等输入。
- 清空并恢复默认与“字段未提交”含义不同，接口必须能区分。
- 不为嵌入模型展示无意义的“最大输出长度”。本期不重新设计嵌入配置界面。
- 本期不新增聊天工具栏开关、预算滑块、思考设置或第三个 token 输入框。

### 4.2 能力获取与优先级

上下文容量来源优先级：用户明确覆盖 → 当前接入服务的可靠元数据 → 与当前模型/渠道匹配的已确认资料 → 未确认默认值。

- 只接收已知语义的容量字段，不从模型名称或“支持 generation”标记推断容量。
- 模型发现得到的输入上限、输出上限、总窗口上限分别保留其语义；不能把输入上限误当总窗口，也不能把不同上限相加冒充能力。
- 本期优先扩展已有模型发现请求可返回的可靠元数据；无对应能力的接口明确走默认或手动配置，不承诺所有服务商均可自动识别。
- 不为每次聊天重新联网发现能力，不通过发送超长内容试探模型窗口，不增加在线模型资料库服务。
- 如果项目尚无经核实的模型容量资料，不为满足流程而猜测填表；该优先级可为空。
- 模型上下文容量和服务商最大输出能力是两个独立事实。只获取到上下文容量时，不能据此推算服务商输出上限，也不能按固定比例将推算值标为“服务商提供”。
- 服务商若明确提供最大输出能力，保存为能力约束；产品的默认生成额度仍为 8,192，而非自动采用服务商允许的最大值。未提供时将服务商输出能力标为未知，使用默认或用户设置的生成额度。
- 自动刷新不覆盖用户手动值。连接地址或模型身份改变后，旧连接的自动能力数据必须失效。
- 手动容量代表用户选择的预算边界，不保证服务商接受。已知真实上限仍需约束请求；错误资料或过期能力应能恢复并修正。

### 4.3 未知容量的默认策略

按已确认的 Q1，容量未知时允许使用，建议初始总预算为 32,768 tokens，并明确显示“容量未确认，暂用默认预算，可手动调整”。该数字是待验证的产品默认值，不是对模型能力的声明，不保证任何未知接口都能接受。

- 不把 32,768 作为所有模型的新全局上限；确认或手动配置更大容量后，应允许使用更大的上下文。
- 若已知输出能力小于默认输出值，默认有效输出值可随能力下调，并显示实际值；用户显式填写冲突值时提示修正，不静默覆盖。
- 无法满足输入和输出组合时，发起请求前提示配置或输入问题。
- 对明确的上下文超限错误，本期至少给出可定位、脱敏的提示和调整入口。
- 不要求本期新增自动减半、连续试探、自动改写永久配置等机制；继续使用现有重试/备用路由规则，避免把不确定错误变成隐式重复调用。

## 5. 单次请求预算与历史分配

### 5.1 预算规则

每次实际模型尝试独立计算，采用该次模型配置快照。对于输入输出共享窗口的服务：

```text
可用输入预算 = 有效总窗口 - 本次最大生成额度 - 安全余量
剩余分配空间 = 可用输入预算 - 系统提示词 - 当前问题 - 消息及证据格式开销
```

输入和输出上限分离的服务按对应约束分别核算，不重复扣除生成额度。推理 token 是否占生成额度由实际接口语义决定，不能承诺所有额度都变成可见正文。

对于共享窗口、且最终输入已确定的请求，其输出额度必须同时满足：

```text
本次输出额度 ≤ 用户设置的最大输出长度（未设置则为 8,192）
本次输出额度 ≤ 服务商明确给出的最大输出能力（若已知）
本次输出额度 ≤ 有效总窗口 - 最终输入估算值 - 安全余量
```

组装顺序应先确定有效输出额度，再为输入留空间。用户提高输出设置后，通过调整可裁剪的历史及资料满足预算；不为了保留全部旧输入而偷偷降低用户明确设置的输出额度。若系统提示词及当前问题等不可裁剪输入仍放不下，则在请求前明确提示。只有上下文容量而没有服务商输出能力时，第三条仅表示空间够用，不构成服务商必然接受该输出额度的保证。

- 取消输出恒定占总窗口 20% 的规则。
- 当前问题和系统指令必须完整保留；固定输入本身放不下时明确提示，不静默截断问题。
- token 计数可使用适配的本地计数能力；没有匹配计数器时使用保守估算并标明估算。中文、无空格英文、代码、标点和长 URL 都要覆盖。
- 安全余量作为内部可调参数；初始建议为窗口的 10% 且至少 512 tokens，最终结合估算误差验证。该建议不能被描述为精确计数保证。
- 1M 等较大配置应能保存并在预算中生效；更大容量是可用上界，不意味着自动扩展到满窗口。

### 5.2 历史消息

- 按当前问题之前的时间边界读取当前会话历史；重新生成旧回答时不混入该问题之后的对话。
- 基于真实回复关联选择完整的用户问题及有效助手回答，不仅按相邻位置凑对。
- 排除被替换、失败、取消、正在生成的助手内容；当前问题不作为历史重复发送。
- 先为最近完整问答保留额度，再装检索资料。初始建议预留剩余分配空间的 25%，比例属于待验证内部参数，不增加前端设置。
- 历史不足时把空余额度交给资料；资料不足时可增加更早完整问答。总量仍受预算约束。
- 单轮历史过长时不能只保留其助手回答或破坏配对；允许整轮省略，并在诊断记录中注明。不能承诺有限窗口内保留所有历史。
- 历史裁剪只影响本次发送，不删除用户的聊天记录，不新增模型摘要调用。
- 为生成请求按需读取最近历史及必要关联，不再为了组装上下文加载全部历史引用。保留聊天列表原有展示行为。

## 6. 检索规模与证据组装

### 6.1 保持项目级范围

仍然使用当前项目的正常资料及其当前就绪版本。保持项目隔离、版本校验、嵌入空间有效性检查；检索故障继续报告，不伪装成“没有相关资料”。

### 6.2 用资料预算驱动规模

- 移除聊天最终资料固定 32 片段的产品限制；最终数量由片段长度、相关性、去重结果和可用 token 共同决定。
- 候选查询需要有界，但当前固定 200 不能继续成为不可调整的全局天花板。候选规模应结合资料预算、片段长度及项目有效规模计算，并支持受控扩展。
- 使用现有关键词与向量结果及融合排序；不增加每轮模型分类、模型重排或全文阅读。
- 项目很大但相关结果很少时，不为凑预算加入任意无关材料。
- 候选停止和扩展规则应确定、可测试；不得将跨查询不具可比性的排序分数当作统一“相关概率”。具体候选倍率、保护阈值以第 10 节样本测试定值，不宣称未经测试的最佳值。
- 同一问题、相同预算和相同资料下，结果应尽量稳定；大的预算允许容纳更多有效证据，而不是仅增加重复邻居。
- 如果内部保护阈值而非 token 预算导致停止，应记录原因，便于区分保护限制和资料耗尽。

### 6.3 复用并修正现有结构补充

- 复用已有的去重、来源分散和相邻段落补充，不新增独立重排服务。
- 避免某一个长章节的邻居占满全部证据空间，挤掉其他高相关结果。
- 合并重叠文本时保留出处；同一张表的不同有效部分不能仅因“属于同一表”就被误删。
- 优先保留完整段落、表格结构。必须裁剪时记录裁剪事实，不能把半张表标记成完整表。
- 扩大候选和引用规模时，避免每个片段重复读取整篇文档、重复查询相同元数据；优先使用现有数据库和批量查询能力，不引入外部依赖。

## 7. 引用全链路兼容

同步检查共享校验、模型提示、流式缓冲、解析、持久化、前端渲染、引用详情及重新打开会话后的加载。

- 支持 S33、S100 及预算允许的更大编号；仍仅接受合法的正整数编号。
- 只将本次实际发送证据中存在的标签绑定为有效引用，不能因为放宽编号就信任模型编造的标签。
- 保持代码区域引用处理、恶意标记防护和项目所有权检查。
- 引用必须定位到实际证据片段；历史引用编号不能错误绑定到本轮同号的其他资料。
- 每次备用模型尝试重新裁剪证据时，同步建立该次请求的标签映射，最终只保存成功尝试的映射。
- 旧的 S1～S32 回答、已保存引用和引用打开行为保持兼容，不迁移或改写旧回答正文。
- 大量引用落库不能继续假设“数量很小”；核对重复消息读取和逐条事务开销，在现有数据库机制内做必要批量处理。

## 8. 路由、输出结束与传输边界

### 8.1 备用模型

- 为每个实际尝试的模型核算容量、输出上限，并从原始资料候选和有效历史重新组装请求。
- 不能只把主模型的长请求换一个模型 ID 后发送，也不能一开始就按所有备用模型中最小的窗口限制主模型。
- 主模型和备用模型使用同一份本轮资料/历史依据；候选不足时可按需扩展，但不必为每个备用模型预先重复检索。
- 若固定输入无法适配当前尝试，明确记录无法适配；在尚无正文输出时可考虑下一个已配置且可用的路由。没有可用路由则返回明确错误。
- 保持现有身份验证失败等不可切换错误的规则，以及已经输出正文后不自动切换的边界。
- 发送、重新生成和现有重试均适用，实际使用模型、用量和结束原因一致落库。

### 8.2 达到生成上限

采用用户确认的“保留回答 + 上限提示 + 继续生成按钮 + 重新生成/设置入口”方案：

- 有正常终止信号并明确达到输出上限时，保留正文和引用，显示“已达到生成长度上限，回答可能未完成”。
- 建议完整提示：“已达到本次输出上限（{limit} tokens），回答可能未完成。可继续生成、重新生成，或在‘编辑模型配置’中提高最大输出长度。”其中数值取该次请求实际发送的额度；确实无法确定时不展示猜测数值。
- 在提示附近提供“继续生成”按钮，复用现有“重新生成”能力，并提供“编辑模型配置”入口，定位到实际生成本条回答的模型。若该模型已删除，说明不可编辑，不误打开同名其他模型。
- 重新生成不接写旧内容，不自动增加额度；沿用现有回答替换/历史保留机制。提高设置后的下一次请求使用新值；若备用模型实际接管，仍按备用模型自己的配置执行并反映实际模型。
- 当已有配置达到服务商已知输出能力时，明确提示不能继续提高；不展示无条件“提高即可解决”的承诺。
- 该状态不能被展示成网络失败，也不能毫无提示地伪装为完整回答。
- 复用消息已有结束原因信息；是否需要新增状态由最小兼容实现决定，不强制重构消息状态机。
- 只收到推理消耗而没有正文时，不能显示空白成功；有明确长度终止原因则显示对应解释，否则保持不完整响应的错误语义。
- 普通完成、用户取消、异常断流和真实服务错误保持区分；不根据文字是否“像没写完”猜测结束原因。
- 只有用户点击“继续生成”才发起续写，不自动补发请求。保持原额度重新生成或继续生成，均允许再次触发上限提示。

#### 手动继续生成

- 按钮用于存在可见正文、未被替换且仍是当前会话最新回答的消息，触发条件为明确因输出上限停止，或从该状态发起的续写被取消/中断后由用户再次尝试。旧回答之后已有新对话时不直接向旧消息追加，避免打乱问答顺序；没有正文时提供重新生成/配置入口，不将空白请求称为续写。
- 点击后基于原问题、已有回答全文、原轮必要历史和原轮有效证据，明确要求接着未完成位置回答。不能调用“重新生成”后将新的完整答案冒充续写。
- 界面在同一条助手回答末尾流式追加，不新建一条用户问题，不覆盖或删除已有正文。Markdown 和引用在合并后仍可正常解析。
- 续写固定使用原回答实际生成的模型配置，使用该配置当前生效的输出上限；模型已删除、禁用或不可用时明确提示，不静默换模型接写。用户可选择重新生成并走现有模型路由。
- 原轮证据标签及其来源映射保持不变，不重新搜索后复用同号标签指向不同资料。为本期新回答持久化或可靠恢复必要的请求依据，优先复用现有消息及资料版本，不保存凭据或重建完整资料副本。
- 原证据已删除、必要版本不可恢复、旧回答缺少足够依据时，明确说明无法安全继续，并提供重新生成；不假装已恢复原上下文。
- 每次续写重新核算输入预算，已有回答全文也计入输入。可减少较早历史和非必要证据，但不能默默丢弃原问题、已写正文或已经引用资料的对应关系；仍放不下时提示上下文不足，不自动摘要、无限续写或强发超限请求。
- 每次续写默认仍最多生成 8,192 tokens，或使用该模型的新设置。再次达到上限时保留新增内容并再次显示按钮；正常完成后移除本次上限提示和继续按钮。
- 生成中禁止重复点击和并发发送，复用停止能力。停止或异常中断时保留原正文和已经收到的新增正文，区分续写中断与原回答失败；用户可手动再次尝试接着当前保留内容续写。没有任何新增内容时原回答不变。
- 应用重启后保留已追加内容及可恢复的续写状态。各次请求用量按同一回答累计，当前截断提示使用最近一次请求的实际上限，不能把多次额度合成一次服务商上限。
- 指示模型避免重复；仅对能够确定的边界重叠做处理，不承诺语义无缝，也不为消除重复而改写用户已看到的原正文。

### 8.3 长响应和超限错误

- 检查现有 1 MiB 流式累计响应限制与新的输出配置是否匹配。事件封装、思考事件和正文都会消耗传输字节，不能简单等同于正文长度。
- 若调整限制，应区分流式生成与普通 JSON，保留有限的响应、单事件/未完成缓冲区保护；不得直接取消所有字节保护。
- 保留连接超时、流式空闲超时和取消能力，不用一个固定总时长截断持续正常输出。
- 对预算/输出参数相关的服务错误，读取有大小限制的错误信息并提取必要的状态、代码和简短原因；脱敏后展示。不得记录 Key、完整请求正文或任意服务端回显。
- 没有明确证据时不把普通 400、网络错误或截断一律归因于 token 超限。

## 13. 数据模型与迁移

### 13.1 模型配置：覆盖值与服务商能力分开保存

015 在 `model_profiles` 增加三个可空列：

| 数据库列 | 类型/默认值 | 含义 |
| --- | --- | --- |
| `context_tokens_override` | INTEGER / NULL | 用户手动容量；NULL 为恢复自动/默认 |
| `max_output_tokens_override` | INTEGER / NULL | 用户手动输出额度；NULL 为默认 8,192 或更低的已知能力值 |
| `generation_limits_json` | TEXT / NULL | 主进程确认的能力、来源和连接身份，不能由 renderer 自报 |

两个整数列使用正整数 CHECK；接口额外要求 `Number.isSafeInteger`，统一数值输入保护上界为 2,147,483,647，支持 1M 等配置。这个保护上界不表示模型能力。JSON 非空时必须通过对应 Zod schema，坏缓存回退为未知并保留可定位诊断，不阻止全部模型列表加载。

标准化能力结构：

```ts
type GenerationLimits = {
  contextWindowTokens?: number; // 共享总窗口；确有该含义才填写
  inputTokenLimit?: number;     // 单独的输入上限
  maxOutputTokens?: number;     // 服务商单次生成上限
  windowKind: "shared" | "input-only" | "unknown";
  source: "provider" | "verified";
  observedAt: string;
  identity: { provider: ProviderKind; baseUrl: string; modelId: string };
};
```

规则：

- `ModelProfileInput` 继续只接收现有提供商配置字段；`ModelProfileDto` 增加高级参数和只读能力信息。不要因为将 DTO 展开传给现有保存接口而破坏 `.strict()` 校验。
- `SettingsRepository.saveProfile()` 的旧 INSERT/UPDATE 不写上述覆盖列，更新提供商时自然保留高级配置；新增 `updateGenerationSettings()` 只写这两列。
- `generation_limits_json` 只由主进程依据同一次实际连接的发现结果写入；不允许 renderer 在保存高级参数时提交。
- provider、规范化后的 baseUrl、modelId 改变时清除旧能力缓存；手动覆盖保留并显示“手动”。Key 更新可能改变接入权限，相关自动能力缓存也需失效。
- 不在 JSON、日志或连接身份中保存 API Key。地址规范化复用现有连接绑定约定，不自行按模型名称合并配置。
- 为新配置写入默认行为时保持覆盖列 NULL，不把 32,768/8,192 写成用户手动选择。服务商能力未知和用户设置值必须可区分。

### 13.2 生成上下文：最小持久化结构

016 新增一张表，不修改 `messages.state` 的现有 CHECK：

```sql
CREATE TABLE chat_generation_contexts (
  message_id TEXT PRIMARY KEY REFERENCES messages(id) ON DELETE CASCADE,
  snapshot_json TEXT NOT NULL CHECK(json_valid(snapshot_json)),
  runtime_json TEXT NOT NULL CHECK(json_valid(runtime_json)),
  revision INTEGER NOT NULL DEFAULT 0 CHECK(revision >= 0),
  active_request_id TEXT UNIQUE
);
```

`snapshot_json` 保存版本化的恢复依据：

- `version: 1`、projectId、conversationId、原 questionMessageId 及其正文 hash。
- 系统提示词原文及版本、原轮 thinking 值；没有原始密钥或连接认证头。
- 实际采用的 profileId、provider、modelId、连接身份 hash，防止同一 profile 被换成另一个模型后继续旧回答。
- 已采用的历史消息 ID、顺序、正文 hash；历史内容复用 messages，不重复保存整段会话。
- 本次实际发送的全部证据列表，不只是模型最终引用过的证据。每项含 label、sourceId、revisionId、chunkId、contentHash、显示名称、locator、原文切片边界及是否添加裁剪标记。
- 每项还保存渲染规则版本及渲染文本 hash，保证还原后的片段与当时发送内容一致。切片边界明确使用 UTF-16 code unit，与 JS 字符串 API 一致，但切割时不得拆开代理对。
- 资料正文复用原版本 `source_chunks`；系统不为续写另存全文副本。恢复时验证 source 仍 active、版本仍存在且 ready、hash 一致，不能偷偷换成新版本。

`runtime_json` 固定为下列职责，不成为任意配置袋：

```ts
type GenerationRuntime = {
  version: 1;
  operation: "initial" | "continue";
  status: "idle" | "running" | "interrupted";
  lastRequestId: string | null;
  finishKind: "stop" | "length" | "context-limit" | "other" | null;
  rawFinishReason: string | null;
  outputTokenLimit: number | null;
  baseUsage: TokenUsage | null;
  attemptUsage: Partial<TokenUsage> | null;
  usageComplete: boolean;
  lastError: AppErrorDto | null;
};
```

`TokenUsage` 沿用现有 inputTokens/outputTokens/totalTokens。用量未知不伪装成服务商真实返回的零；若兼容现有 DTO 必须以零占位，`usageComplete=false` 必须保留。

初次生成在每次尝试准备完成、真正发送前保存该次快照；无正文输出的失败尝试可以被下一尝试替换。一旦产生正文，不再更换该回答的证据及模型身份。续写不重建、重排或重新编号原快照。

`MessageDto` 增加可选 `generation` 摘要，包含 revision、status、finishKind、outputTokenLimit、canContinue、blockedReason、lastError、usageComplete；不把 `snapshot_json` 整体发送到 renderer。旧消息没有摘要时仍正常展示，缺少快照的旧截断回答可重新生成，但不假装能够续写。

### 13.3 事务、删除及恢复

- 开始续写使用 `revision` 比较和 `active_request_id IS NULL` 做 CAS；影响行数必须为 1。消息所属项目、会话、最新有效回答、未删除/归档等检查在同一事务内完成。
- 同一 requestId 正在运行时返回冲突，不再调用服务商；已经结束且等于 lastRequestId 时返回已有结果，不重复结算，并向该次已建立的订阅重发权威终态，避免 hook 永远等待事件。这一幂等命中先于 expectedRevision 检查，但仍必须先校验所有权。其他旧 revision 的迟到请求返回 CONFLICT。
- 每次 checkpoint 在同一事务保存“当前完整正文 + 当前用量快照 + runtime + revision”；采用替换式快照，不对同一 usage 事件重复累加。
- 最终事务一次完成正文、引用、用量、结束原因、runtime 和 active_request_id 清理；只有事务成功后发终态事件。
- 普通初次生成继续按现有中断恢复规则处理。续写运行时中断恢复为 `messages.state='completed'`、runtime interrupted、active_request_id NULL，保留已落库正文，绝不能由旧恢复逻辑变成空白取消回答。
- 保留现有 checkpoint 频率时，崩溃最多丢失最后一个未持久化窗口，不能声称逐 token 持久化。正常取消/断流必须落最后一个 checkpoint；重启以数据库为准提示续写中断，不从头重复追加。
- 物理删除消息/项目时依赖 FK 级联清理快照；软删除/归档后禁止继续生成。来源删除导致引用数据变化时重新判定可恢复性，不跨越删除权限恢复资料。

## 15. 容量解析、计数与上下文算法

### 15.1 有效能力

`generation-limits.ts` 实现纯函数 `resolveGenerationLimits(profile)`，返回窗口类型、有效窗口/输入上限、已知输出能力、用户目标输出及来源说明。

- 默认窗口 32,768、默认输出 8,192，统一常量命名，禁止在多个 provider 分别复制默认值。
- shared：用户 context 覆盖总窗口；input-only：用户 context 覆盖输入额度，界面说明其含义；unknown：保守按 shared 处理。已知 input 和 shared 约束同时存在时同时遵守。
- 手动容量可以主动降低预算，但不能突破同一语义的已确认能力。保存时若大于已知上限则报字段校验错误；能力刷新后旧手动值产生冲突，也在发送前提示修正。不静默截短手动值，更不能把它当作修改了服务商真实能力。未知能力时允许保存较大值并保留“未确认”的说明。
- 用户显式输出大于已知服务商能力时保存失败；旧配置在能力更新后变为非法则请求前给出明确冲突，不静默降低手动值。
- 没有手动输出时，可按已知服务商输出能力将默认值向下收敛。不得从大上下文按比例提高输出。
- 若小窗口连默认额度与系统/当前问题都容纳不了，允许仅对“默认输出”下调至可容纳额度并显示实际值；手动输出不自动下调。下调后少于 1 token 则拒绝发送。
- 计算前验证元数据和全部算术的有限性；不得将缺失字段用 0 表示实际能力。

### 15.2 计数的第一版实现

本期不增加分词依赖。将聊天计数规则收敛到 context-builder 的一个入口；工作台使用的 chunker 估算保持不变。

- 有经过验证的匹配模型计数器时可用其计数；没有时第一版使用 `ceil(Buffer.byteLength(text, 'utf8') / 2)` 作为可校准估算，另计算角色、消息分隔和证据包装开销，并标记 `estimated=true`。替换现有按空白切词的估算，防止一整段无空格代码或 URL 被算成一个词。
- 这个字节系数只是待验证的内部起点：不同语言、随机字符串和不同 tokenizer 都可能高估或低估，叠加安全余量也不是数学保证。不得把原始 UTF-8 字节数直接当日常 token 数，从而把普通中文预算固定放大约三倍；必须对比同窗口下实际保留的证据与历史量，避免计数改动成为新的隐形限制。留下 `ponytail:` 注释说明“按本地固定样本校准；有匹配 tokenizer 时替换”，不把估算量展示为实际计费 token。
- 每条消息按 `estimate(content) + 8`，请求额外加 64；证据标题、locator、标签、围栏和裁剪标记按实际组装文本计数，不再只数原文。
- 安全余量 `S=max(512, ceil(C*0.10))`；shared 输入上界 `I=C-O-S`；input-only 为 `I=C-S`，若还有已知共享窗口，则再取 `min(I, sharedC-O-sharedS)`。
- 即使估算保守，仍需处理服务商明确超限错误；不能将“估算通过”当作真实服务保证。
- 组装结束后再计数整个消息数组。超出上界时按“补充历史 → 低优先级证据 → 预留历史”的顺序回退；系统指令、当前问题及续写已有正文不可裁剪。

### 15.3 历史查询与分配

在 ConversationRepository 新增 `listHistoryPairs({ projectId, conversationId, beforeSequence, cursor, limit })`。按用户问题的 sequence 逆序，连接 `assistant.reply_to_message_id=user.id`，仅选 active lineage、双方 completed、非空正文。

- `beforeSequence` 为当前用户问题序号；重新生成也以原问题为界。
- 使用 sequence 游标分页，每页 32 对；只返回 ID、sequence、content、角色和必要 hash，不加载 citations 的详情与预览对象。
- 现有 UNIQUE(conversation_id,sequence) 和 active lineage 索引优先复用；先检查查询计划，再决定是否新增索引。
- 扣除固定输入后的空间为 R，历史初始额度 `floor(R*0.25)`。从最近完整轮开始加入，遇到首个放不下的整轮停止，保证保留的是连续的最近上下文，不能跳过最新问题却塞入更旧回答。
- 没有历史时额度全部让给证据；有历史但最新一轮大于历史额度时，整轮省略，保留原因。资料用完后还有空位，可再从同一历史边界扩充。
- 资料的初始额度为 `R-实际保留历史量`，而不是机械扣掉未用完的预留。
- 发送用的旧助手引用标记改为不与本轮 S 编号混淆的文字，例如“前轮引用”；只处理非代码中的有效旧引用，保存的旧回答不改。本轮续写的原回答不做这种替换，因为其证据映射必须延续。

### 15.4 组装结果契约

`assembleContext()` 返回 `messages`、`tokenBudget`、`selectedEvidence`、`historyMessageIds`、`diagnostics`。`selectedEvidence` 包含实际发送的文本范围、标签、原始 chunk/revision/hash，用于引用和续写快照。

标签在筛选、裁剪完成后分配，初次生成从 S1 连续编号；续写使用固定原标签，删除可选证据时允许留编号空洞，绝不重新编号。文本不足时允许少发，不以填满容量为目标。

## 16. 自适应检索的明确执行规则

### 16.1 接口和默认参数

保留现有供其他调用方使用的 `search({ projectId, query, limit })`。为聊天在同一 RetrievalService 中增加 `searchForChat({ projectId, query, evidenceTokenBudget, signal })`，共用嵌入空间检查、召回和权威资料过滤，不复制另一套检索实现。

初始内部参数（可调且必须写入基准结果）：

| 参数 | 起点 | 作用 |
| --- | --- | --- |
| 首轮每路候选 | 96 | 大模型也从小查询开始 |
| 扩容倍率 | 2 | 96、192、384……，不一次读满项目 |
| 候选保护上限 | 4,096 / 每路 | 防止局部查询无限增长，非最终 32 片段限制 |
| 候选正文累计保护 | 32 MiB | 记录 resource-limit，不默默装作资料耗尽 |
| 相对融合分数下界 | 首位分数的 0.20 | 仅本查询内的启发式裁剪，不是概率或跨查询阈值 |
| 邻居额度 | 证据预算的至多 25% | 防止一个章节邻居挤掉独立命中 |

### 16.2 处理步骤

1. 校验项目、当前 embedding space 及 fingerprint。对当前 query 只计算一次 embedding；整个扩容过程复用。
   当 evidenceTokenBudget 不足以容纳最小证据包装时直接返回 budget，不调用 query embedding 或检索。首轮没有有效结果不自动等同于耗尽：只有两路原始结果均少于各自请求量，才有候选耗尽依据。
2. 保持项目过滤下的向量和关键词查询。两路结果按已有 RRF 融合；不要把 Promise 并行调用误当作底层一定并行，Lance 的现有表级锁仍生效。
3. 以最多 400 个 chunkId 一批查询 SQLite 权威数据，带项目、active、当前 revision、ready 条件。把 displayName/kind/locator 一次带出，移除 index.ts 对每个结果的额外 lookup。
4. 对本轮有效候选计算估算成本中位数 `m=max(64, median(cost))`；候选目标上界为 `min(4096, max(96, ceil(evidenceTokenBudget/m)*4))`，若已知项目有效片段数更小再取较小值。不为计算数量把整个 Lance 表加载到内存。
5. 用本查询首位融合分数的 20% 保留相关候选，再复用现有来源/相邻位置分散排序和确证去重。向量近邻不等于必然相关，这个门槛有漏检风险，必须在基准中记录并校准，不能声称全面覆盖。
6. 优先放独立命中，再用剩余邻居额度补充最多前后各一个相邻片段或明确可识别的表格结构。若核心片段本身就是完整表格，不重复添加同一内容的邻居。
7. 当前最终片段已满足证据预算，则停止；否则，只要仍可能存在候选、未触及候选/字节保护且尚未连续两次扩容无新增有效正文，就按倍率扩容。首次扩容不要求预先证明后续会有新增；单路耗尽后只扩展另一路。当前所有候选无效而无法计算 m 时，按倍率继续到资源保护或真实耗尽，不因缺少中位数提前返回空结果。
8. 停止原因必须区分 budget、exhausted、relevance-tail（连续两次扩容无新增有效正文）、candidate-limit、resource-limit、cancelled。扩容结果是重算后的权威候选集，不能把同一片段多次追加。

这个上限属于有界检索保护，意味着自动链路可能仍未覆盖全部相关资料；符合本期不做全面阅读的范围，但必须公开在诊断中，不能宣传为“无限片段”。增加 4,096 保护值必须有性能证据，不增加用户配置项。

### 16.3 同时需要修正的实现细节

- `stableSearch()` 当前同分结果会不断翻倍查询；增加扫描保护与 signal 检查，同分排序仍稳定。达到保护时返回有界结果和原因，不能绕过上层候选限制。
- 批量权威过滤在 RRF 最终截取前完成，避免旧 revision 占满前列，排挤当前资料。
- 去重不能只按“同一张表”认定内容相同。相同原文可保留一个代表；不同表格部分分别保留来源。第一版不把不同来源或 locator 合成无法追溯的单一证据标签。
- 邻居读取限定命中 revision 及所需 ordinal 范围；不为每个命中反复读取整篇 revision 的所有正文。
- 所有 CPU 循环在批次边界检查 abort。检索调用返回后到真正发送前，再核验选中资料未被删除或替换；有变化则重新准备本次上下文或明确停止，不使用失效快照。

## 17. 模型发现、路由及 provider 请求

### 17.1 自动能力接入

- 在 `ModelDescriptor` 和 `modelDescriptorSchema` 增加可选 `generationLimits`。缺失不影响发现；已出现但格式错误的可选元数据忽略并记录诊断，不把整个模型列表判成不可用。
- Gemini 现有 models 请求中，按已确认字段语义接收 `inputTokenLimit`、`outputTokenLimit`，分别映射 input-only 与最大生成能力。
- 其他 provider 仅映射其协议有可靠定义的字段；实现阶段需用相应官方响应定义和本地 fixture 确认。不能把接口任意名为 context/max_tokens 的字段直接认定成容量。拿不到就用未知，不新增探测调用。
- `discover()` 与 `saveProfile()` 中现有 test/discovery 得到的数据由主进程按同一连接身份持久化；新模型第一次保存时也要能落库。不能依赖 renderer 把发现结果重新提交为可信能力。
- 不在每轮聊天中刷新；旧模型没有缓存时依然可用默认值，下一次已有的模型发现/测试可更新数据。用户打开高级编辑窗口本身不发测试请求。
- 本期不强制新增内置型号表；没有已确认资料就跳过 verified 分支。

### 17.2 每次尝试准备请求

在现有 `generateRouted` 增加主进程专用、可选的末尾参数，保留所有原调用方：

```ts
type PrepareAttempt = (
  profile: ModelProfileSnapshot,
  attemptOrder: number,
  signal: AbortSignal
) => Promise<GenerateRequest>;
```

- 现有静态 request 继续提供 projectId、operationId 和非聊天调用的默认行为；只有聊天传入 prepareAttempt。该函数不经过 IPC，也不序列化到服务商请求。
- 路由在每次尝试的 try 内、调用 provider.generate 前执行准备；ChatService 闭包负责该 profile 的预算、历史、资料候选和快照，不把 RAG 逻辑塞入模型路由。
- 一个用户请求内，配置及来源版本采用一致快照；缓存 query embedding/已取候选，备用小窗口只重新裁剪。备用大窗口需要更多候选时可扩展原次检索，但必须重新验证来源版本，不能混用两次项目快照。
- 回调成功后更新本轮有效引用映射、输出额度及持久化依据；在准备失败/没有正文的失败后允许下一次重建。一旦文本发出，原有不切换规则继续成立。
- 预算不足用结构化的 `ProviderRequestError` 表示，code=VALIDATION、messageKey=errors.contextBudgetExceeded；仅这种发送前不可适配情况允许尝试下一个 route。AUTH、未知 400、用户取消不因此变成可切换。
- 历史/SQLite/引用准备的程序异常不是容量问题，不标记 fallbackEligible=true 来掩盖。
- 续写使用只返回原实际 profile 的 router 适配，不调用会追加备用列表的普通显式 override 路由。原 profile 存在但 modelId/baseUrl 已变化时提示上下文不可恢复。

### 17.3 额度和结束原因

保留统一 `GenerateRequest.maxTokens`，在各 provider 映射到实际请求参数。当前代码的 OpenAI-compatible 为 max_tokens、Anthropic 为 max_tokens、Gemini 为 maxOutputTokens、Ollama 为 num_predict；涉及协议必须用其他参数的模型，按已确认适配规则处理，不在同一个请求同时发送互斥额度字段，也不通过反复增加额度测试兼容性。

新增纯函数 `normalizeFinishReason(provider, rawReason)`，至少覆盖现有协议的 length / max_tokens / MAX_TOKENS 与正常 stop/end_turn/STOP。context-window-exceeded 归为 context-limit，不错误提示只提高输出就能解决。内容过滤、拒答、工具调用、缺失终态不能映射成 length。原始 reason 仍保存以便诊断。

`generateRouted` 当前“没有可见文本即 incomplete”的规则需要补充：有明确 length 终态但无正文时返回可识别的 output-limit-empty 错误，不显示空白成功、不自动高额度重试；没有明确终态仍为 incomplete。

OpenAI-compatible 现有 thinking 方言探测会把部分 4xx 当作方言拒绝重试。识别出 context/output-limit 错误后必须直接上抛，不能为同一个超限请求轮流尝试所有 thinking 方言。

## 18. 继续生成：执行步骤与状态机

### 18.1 主进程执行路径

1. `ChatService.continueAnswer()` 校验 requestId、所有权、会话可用性、最新回答、有效快照、expectedRevision 和可续写终态；同步占用现有会话 in-flight 锁，再做异步准备。
2. 验证原 question hash、模型身份、证据版本和 hash。恢复必要历史和证据；可选历史损坏则省略并记录，原问题或必需证据损坏则拒绝。
3. 依据原实际模型的当前配置计算预算。固定输入为原系统指令、原问题、已有完整回答、续写指令，以及已有回答已经引用的有效证据。其余原证据和历史按原顺序补入。
4. 续写消息顺序：系统指令 → 必要历史 → 原证据块（保持 S 编号）→ 原问题 → 已有助手正文 → 简短用户续写指令。指令要求从中断处继续、避免重述、沿用原引用，但不持久化成一条用户聊天消息。
5. 固定输入仍放不下时返回明确的 CONTEXT_BUDGET 错误语义，不裁剪已写正文。若原回答有无法验证的引用标记而不能判断必需证据，保留全部原证据；仍放不下就拒绝，不猜测。
6. CAS 标记 context runtime running/continue 并锁定 requestId，messages.state 设 streaming，正文保留。开始事件携带完整旧 message；不调用 startAssistantMessage 或 regenerateAssistantMessage。
7. 从旧正文长度开始发送 delta；每个 checkpoint 替换完整正文，记录本次 usage 的最新累计值。记录最后一次有效活动，取消检查覆盖准备与生成全过程。
8. 结束时合并正文后完整重解析引用；一个事务更新结果。正常 stop、再次 length、取消或异常各按下表落库并发终态。
9. finally 释放请求及会话锁。数据库终态提交失败时，不发伪造 completed；保留可恢复的 running 标记供后续恢复，返回 INTERNAL。

### 18.2 状态表

| 事件 | messages.state | runtime.status / finishKind | 正文处理 | UI |
| --- | --- | --- | --- | --- |
| 初次生成正常完成 | completed | idle / stop | 保存新正文 | 普通回答 |
| 初次达到输出上限且有正文 | completed | idle / length | 保留新正文 | 提示、继续、重生成、设置 |
| 开始继续 | streaming | running / 保留上次原因 | 保留原文并追加 | 正在续写、可停止 |
| 续写正常完成 | completed | idle / stop | 合并保存 | 移除上限提示及继续按钮 |
| 续写再次达到上限 | completed | idle / length | 合并保存 | 再次显示继续按钮 |
| 续写被用户停止 | completed | interrupted / 保留原因 | 保留原文和新片段 | 已停止续写、可继续 |
| 续写超时、断流或错误 | completed | interrupted / 保留原因 | 保留原文和新片段 | 续写中断及脱敏原因、可再试 |
| 续写中应用崩溃 | 恢复为 completed | interrupted | 恢复最后 checkpoint | 续写中断、可继续 |
| 固定输入放不下/证据失效 | 不改变 | 不伪造运行状态 | 原文完全不变 | 明确说明不能继续，提供设置/重生成 |

只有原回答本来可续写的状态允许 interrupted 后再续写；不能借这个入口给普通已完成答案无限追加。取消或失败没有新增片段时也不损坏原回答的状态和引用。

### 18.3 引用与文本边界

- `citationLabelSchema` 改成正整数编号，使用 JS safe integer 数值校验；解析、宽松诊断、stream buffer、Markdown 识别同步支持三位及更多编号。前导零、负号、伪造标签仍不接受。
- CitationStreamBuffer 对不完整引用的尾部缓冲有确定上界（按最大安全整数标签长度），恶意超长 `[S111...` 不能无限占用内存。超界原样作为普通文字输出，不生成引用。
- 续写可能接在半个 `[S`、Markdown 围栏或表格后；正文合并后再解析，引用 start 按合并后的完整 JS 字符串位置计算，不能使用本次片段的局部位置。
- 初次回答和续写终态都采用 `replaceMessageCitations()`：验证所有权一次，在同一事务按合并正文生成确定的 `(messageId,label,start)` 记录。复用既有定位及 quote 逻辑，消除逐条反复读取消息的开销。
- 可在 checkpoint 同步更新当前可解析引用，或在中断/重启恢复时补齐；重启后不能显示新增正文但永久缺少它的引用。
- 第一版只用提示约束模型避免语义重复，不引入模糊匹配删文算法。传输重复由 offset 防重解决，不能把模型主动重复的相同短句直接当作传输重放删掉。

### 18.4 用量结算

续写开始时保存已有回答的 baseUsage；本次 usage 事件是累计快照，覆盖 attemptUsage 而非相加。当前展示用量为 baseUsage + 最新 attemptUsage，最终一次写入 messages.usage_json。

重复终态通过 active_request_id/lastRequestId 阻止二次结算。中断时没有本次 usage 就保留已知基础用量并设 usageComplete=false，不根据可见正文估算成服务商实测用量。下一次续写以已知累计值为基础，不能把前次已结算 attempt 再加一次。

## 19. 长流边界与错误详情

### 19.1 有限的响应预算

扩展 `HttpRequestOptions` 为内部选项时，必须在构造 fetch RequestInit 前剥离这些字段，不能作为 header/body 或 fetch 扩展属性泄漏。

| 读取类型 | 第一版限制 |
| --- | --- |
| 普通 JSON | 维持现有 1 MiB 默认值，嵌入/发现不顺带放宽 |
| 生成流累计字节 | `min(64 MiB, max(8 MiB, 2 MiB + outputTokens * 1024))` |
| 单条事件/未终止事件缓冲 | 1 MiB；按 UTF-8 字节计算 |
| 错误正文 | 最多 16 KiB；读取最长 2 秒，受调用方取消约束 |

这些是有限资源保护起点，不是“任意合法 8K 回复必然小于该值”的保证。超过保护时保留已输出内容并返回明确 responseTooLarge 原因，不误显示 token 截断。调整常量需要对应 fixture 和基准数据。

保持当前连接/响应头 30 秒、流空闲 120 秒的默认语义，不引入总流时长 30 秒限制。已有心跳不代表无限许可，累计字节保护仍生效。SSE 和 NDJSON 拆分时在拼接前检查 pending buffer，防止缺少分隔符绕过单事件限制。

### 19.2 错误传递

- 当前 HTTP 层遇到非成功响应会取消正文；改成受限读取后，只提取状态、已识别的 error.code/type、明确的 capacity/output 数值及 messageKey。
- 使用已有 `AppErrorDto.details`，限定白名单键如 status、providerCode、requestedTokens、limitTokens、profileId。任意原始服务端 message 不直接回显，以免包含问题、资料或凭据；无法可靠脱敏时只显示已识别代码及本地说明。
- 继续复用既有 error code 大类：VALIDATION 表示本地设置/预算冲突，PROVIDER 表示明确服务限制或协议错误，NOT_FOUND/CONFLICT 表示上下文不可恢复；通过独立 messageKey 区分原因，不凭 HTTP 400 猜测。
- 从 HTTP → provider → routed-generation → ChatService → IPC → renderer 保留这些受限 details。新增续写失败事件也使用同一错误 schema。
- providerCode/type 只接受已知枚举或映射为本地类别；未知自由字符串不透传。数值字段验证有限、正整数及合理范围，不把任意服务端字符串放进白名单就当作已经脱敏。
- 网络、身份认证、缺少终态、响应过大、上下文超限、输出参数被拒绝必须有不同可测试分支；不自动调整用户配置。
